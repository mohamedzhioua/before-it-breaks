# Security: threat model and safe use

For anyone who runs the kit, and especially anyone pointing it at code they did not write. This page is the threat model; how to report a vulnerability in the kit is in the repository's security policy.

This kit is **not** a security audit tool. This page is about using it safely.

## Threats

1. **The agents read untrusted code.** Source files, comments, docs, commit messages and config in the audited repos may hold text written to steer an AI (prompt injection), and agents may copy it into maps, candidates and notes. Every agent's instructions say that such text is data, never orders, and the workflows pass earlier results to agents inside fenced, labelled blocks. That lowers the risk; it does not remove it.
2. **The evidence runner executes commands written by agents.** `kit evidence` re-runs them at the pins.
   - It starts no shell: each command is split into words and each pipeline step is started directly.
   - Only a short list of reading programs (git read subcommands, grep, rg, cat, head, tail, sed, wc, sort, uniq, cut, tr, ls) with a per-program list of options is accepted; `awk` and `jq` are never run.
   - Globs, variables, chains, redirects and paths outside the repo are refused.
   - git reads at the pinned commit, with settings that stop a repo's `.gitattributes` from naming filter or diff programs.
   - git also runs without your global and system git config (`kit pin`, `kit doctor` and `kit check unchanged` carry over only `core.autocrlf` and `core.eol`; the evidence runner carries no global or system config), with signature checks, gpg, fsmonitor and attributes files switched off, with fetching blocked, and without looking into submodules.
   - `sed` runs with `--sandbox` when the installed sed supports it (checked once per run; `kit evidence --dry-run` says when it does not).

   **This is an allowlist, not a sandbox.** A flaw in it, or in one of the programs it starts, could still read or do more than intended.
3. **A repo's `.git` folder is trusted input.** git reads `.git/config` and `.git/info/attributes`, and settings there can start programs (a filter or diff driver, a hooks path, a credential helper) or send git to another folder. `kit pin` and `kit doctor` read those files as text before the first git call, and refuse the repo when:
   - `.git` is a file (a `git worktree` or submodule checkout) or a link, or has a `commondir` file or `objects/info/alternates`;
   - the folder is itself a git folder (a bare repository, or a folder inside `.git`);
   - `config`, `config.worktree` or `info/attributes` is not a regular file, is larger than 1 MiB, or cannot be parsed;
   - the config sets `core.worktree`, `core.hooksPath`, `core.sshCommand`, `core.fsmonitor`, `core.askpass`, `core.gitProxy`, `filter.*`, a diff driver's `command` or `textconv`, `diff.external`, `trace2.*`, `gpg.*`, `include.*`, `includeIf.*`, `alias.*`, `credential.*`, `protocol.*`, most `extensions.*`, or a remote's `promisor`, `uploadpack`, `receivepack` or `vcs` (includes are refused on sight, never followed);
   - `info/attributes` names a `filter=` or `diff=` driver.

   The evidence runner and `kit check unchanged` check again. `kit pin --trust-git-dir` pins a repo whose .git folder the check refused. The problems found are then allowed (a .git file, commondir, alternates, core.worktree, includes, filter and diff drivers, so a driver can start a program when git reads the repo). The flag records them plus a digest of the .git control files in `pins.json` and the baseline; `kit doctor`, `kit evidence` and `kit check unchanged` then refuse the repo if any of those files changed since, even an edit the check cannot see, until you clone again or re-pin. The digest covers `.git` itself and `config`, `config.worktree`, `info/attributes`, `commondir` and `objects/info/alternates` in the real git folder, following one `gitdir:` pointer (a worktree or submodule checkout) and one `commondir` pointer; a pointer that cannot be resolved is refused. A file named by `include.path` or `includeIf` is outside the digest, so an edit to it is not seen; do not use the flag on a config that includes another file. The isolated git environment (no signature checks, gpg, fsmonitor or fetching) still applies. A repo pinned with the flag by kit 0.1.0 has no digest and is refused until it is re-pinned. Worktree checkouts and submodules are refused unless `--trust-git-dir` is used. Clone from a remote you trust instead, and for a repo you do not trust run the audit inside Claude Code's sandbox with the network off.
4. **Workspaces hold private material.** Configs, receipts, maps and reports may contain private paths, code excerpts and details of your system.

### How the evidence runner handles `.env` files

A file or folder named .env, or .env followed by '.', '-' or '_' (any case), is never read by name and is excluded from folder searches (grep, rg, git grep). `git show` and `git diff` always get the same excludes, and `git log` gets them with patch or file-list output (`-p`, `--stat`, `--unified` and the like); a file operand that is a link to such a file is refused. Not covered yet: reading a `.env` file by its object id (`git ls-tree` shows the id; `git cat-file -p <id>` or `git show <id>` prints it, since pathspecs never apply to a blob), and `git log --follow` or `-L` (git takes no extra pathspec there, so a `.env` under the named folder, or one renamed to another name, can show its contents). For these the output detectors are the only check. The kit never promises that a secret cannot reach a receipt: the output detectors are the last line, and a withheld output is the signal to look.

The runner refuses such names as file operands, in `rev:path` and as option values, and refuses a grep `--include` or rg `-g` pattern (or a git pathspec after `--`) that names or could match one. For `grep` and `rg` it also adds `.env` excludes just before the first operand (the search pattern or the first path), and for `git grep`, `git show`, `git diff` and `git log` with patch or file-list output exclude pathspecs, so a recursive search or a patch skips them. Search patterns may still mention `.env` (`rg 'process\.env'` runs).

The output detectors are the built-in must-zero patterns of the leak gate plus `evidence.secret_patterns`: home paths, credentialed connection strings and web URLs, JWTs, payment keys, cloud keys, private-key blocks, token prefixes and email addresses. When one matches a command's output, that command's whole output is withheld from the receipt. They are patterns, not proof: a secret in another shape, or a token that directly follows a letter, digit or `_` (for JWTs and Google `AIza` keys, also `-`), is not caught, so a secret committed in a source file, in `.envrc` or in history shown by `git log -p` can still reach a receipt. Keep workspaces private.

## Safe use

- Point the kit only at code you have permission to read.
- Keep agents read-only. `init` writes deny rules into the workspace's `.claude/settings.json` for the command prefixes in `read_only.deny_bash` (`config/defaults.json` holds the full list), and also denies Edit and Write inside each audited repo. The groups: git writes (push, commit, checkout, switch, reset, restore, stash, clean, `git rm`, `git mv`, merge, rebase, pull, apply, am, cherry-pick, revert); package installs (npm, pnpm, yarn including bare `yarn`, bun); download and remote tools (curl, wget, nc, ssh, scp, and the `.exe` forms of curl and wget); interpreters and shells (python, python3, py, perl, ruby, `node -e`, `--eval`, `-p`, `--print`, `-i`, `--eval=`, `--print=`, bash, sh, zsh, powershell, pwsh, cmd); package runners (npx, `npm run`/`exec`/`x`, `pnpm dlx`/`exec`, `yarn dlx`, bunx, `bun x`/`run`); and git commands that reach out or change config (fetch, clone, remote, config, submodule). These rules are **a layer, not a boundary**: they reduce accidents and are not a promise. Bare `node` cannot be denied, because the kit itself runs on it, so a session can still start a Node script; code glued to the option (`node -e"..."`) may also slip past a prefix rule. Run the audit in a container, a VM or Claude Code's sandbox if that matters to you. A rule like `Bash(git * <sub>)` also blocks an unquoted search such as `git grep checkout`, `git grep config` or `git grep fetch`: quote the search word (`git grep 'checkout'`) or use `rg`.
- Review the evidence commands before they run: `kit evidence <ws> --dry-run` lists what would run and what is refused.
- For repos you do not trust, run the whole audit inside a container or VM with the repos mounted read-only.
- Never put secrets in the config; name environment variables instead. Command text in a receipt is masked in place with `evidence.secret_patterns`; when a secret, email or home-path pattern matches a command's output, that command's whole output is withheld from the receipt.
- Keep workspaces private. The workspace `.gitignore` ignores everything by default; run `kit check secrets <ws>` and keep its record before sharing anything. Its home-path and email rules apply to the published set only (the 01–05 outputs, the docs folder, receipts, verdicts, final verdicts and claim verdicts, issues, explorer data and rules results); secret and token patterns apply to every workspace file. The record lists `published[]`, `patterns.{all,published}` and, per hit, `hits[].set`.
- Ask before any check touches a shared environment, and never run load against production.

## In scope for reports

Ways to get the evidence runner to run something outside its allowlist, or to read outside the pinned repos, are security bugs in this kit and in scope for reports. So is a `.git` folder that makes the kit start a program or fetch without `--trust-git-dir` (a gap in the preflight above).
