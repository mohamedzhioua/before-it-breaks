### SVC-REL-01

**A start-up connect or createIndex failure is stored for good in collectionP: the store never retries and every session operation fails until the process restarts**

- **Verdict:** PROVEN-STATIC · **Severity:** High · **Source:** new · **Lens:** reliability · **Repo:** `connect-mongo`
- **Rule that decided it:** survived the skeptics; evidence reproduced
- **Cited code:** `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:226`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:238`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:262`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:384`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:444`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:499`, `connect-mongo@182cfb09ad:src/lib/MongoStore.ts:558`
- **Receipt:** [`354865edab2e`](work/phase3/receipts/SVC-REL-01.md)
- **Claim as hunted:** The store builds its collection handle only once, in the constructor: collectionP = clientP.then(... await createIndex ...). Under the default autoRemove 'native', that promise rejects if MongoClient.connect fails or if createIndex fails. Causes include a primary election or network error at deploy time, MongoDB not yet reachable when the container starts, or an existing 'expires' index with other options, for example one the host created itself as the README advises. Once rejected, the promise stays rejected. Every later get/set/touch/destroy awaits the same promise and fails at once. For each such process, every request that carries a session cookie gets a store error until someone restarts it, even after MongoDB is healthy again. If no store call is waiting at the moment of rejection, nothing has attached a handler to collectionP. Node (15 and later, with no host handler) then treats it as an unhandled rejection and stops the process. So the outcome depends on whether traffic arrived before the failure: either a crash, or a process that stays up but cannot serve sessions. This does not depend on the session count. As more app processes are added to serve more sessions, more of them start during any one deploy or election, so more processes are exposed.
- **Mechanism:** Line 227: `_clientP = MongoClient.connect(options.mongoUrl, options.mongoOptions)`. Lines 238-244: `this.collectionP = _clientP.then(async (con) => { const collection = con.db(options.dbName).collection(...); await this.setAutoRemove(collection); return collection })`. setAutoRemove in 'native' mode returns `collection.createIndex({ expires: 1 }, { background: true, expireAfterSeconds: 0 })` (lines 262-270). collectionP is assigned only at line 238 and never reset. No .catch is attached to it at construction. Every method starts with `await this.collectionP` (384, 444, 499, 530) or `this.collectionP.then(...)` (558, 577, 588), so a single rejection turns into a lasting failure of every method. Nothing retries, rebuilds the promise lazily, or emits 'disconnect'/'connect' events.
- **Arithmetic as hunted:** n/a: not size-driven. One failed start-up call (connect or createIndex) is enough, and the failure lasts until that process restarts. Exposure grows with the number of app processes that start during an unhealthy window, not with the number of sessions.
- **Mitigations looked for:** Retry or lazy re-creation of collectionP: none. It is assigned once at connect-mongo@182cfb09ad:src/lib/MongoStore.ts:238 and never reset (git grep 'collectionP'). · Catch on collectionP at construction: none (connect-mongo@182cfb09ad:src/lib/MongoStore.ts:238-244). Catches exist only per method call (e.g. connect-mongo@182cfb09ad:src/lib/MongoStore.ts:410, 569, 580, 596). · Handling an IndexOptionsConflict from createIndex: none (connect-mongo@182cfb09ad:src/lib/MongoStore.ts:264-270). clear() has a special case for code 26, but only for deleteMany (connect-mongo@182cfb09ad:src/lib/MongoStore.ts:599-604). · Emitting store 'disconnect'/'connect' events that express-session could use to bypass the store: none in src (git grep 'disconnect' is empty). · Docs: README line 202 tells very concurrent deployments to create the index themselves rather than use 'native' mode. That does not prevent the failure: if the host's index has other options, createIndex conflicts and triggers this same path. · Host-side process supervision or an unhandledRejection handler: not visible (library repo, no host app; known gap).
- **Threshold as corrected by the skeptics:** Not size-driven: it can hit any process at any session count. The trigger is narrower than claimed. A short primary election alone probably does not trigger it, because driver server selection waits up to serverSelectionTimeoutMS (default 30 s, unverified), so it needs an outage longer than that at start-up, a network error during the createIndex op, or a pre-existing expires index with conflicting options. The outcome is either a crash from an unhandled rejection (a supervisor restart heals it) or a live process that fails every session request until restarted.
